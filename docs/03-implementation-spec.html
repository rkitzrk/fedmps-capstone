FedMPS — Four-Phase Build Spec

One codebase, built in four sequential passes. Nothing runs until all four are done, so the interfaces between them are frozen up front — that is what makes deferred testing survivable.

Package fedmps Phases 4 sequential Files 23 Est. LOC ~1,400 Testing After Phase 4 Status Awaiting your sign-off

Because nothing is executed until the end, every phase boundary is a written contract rather than a passing test. Phases 2 and 3 are built against fixed array shapes and a dummy backbone, so they stay testable even if the face model never installs.

Ground rules for this build

Four decisions that make deferred testing safe

  1. Contracts frozen in Phase 1. Array shapes, dtypes, file names and the config object are all fixed in the first pass and never renegotiated. Later phases read them, they do not change them.
  2. A dummy backbone ships in Phase 1. DummyBackbone emits deterministic 512-d vectors with real identity structure — same identity clusters together, different identities do not. The entire learning and privacy stack can therefore be exercised without insightface, torch vision weights, or a single image. This is the single most important de-risking decision in the plan.
  3. Privacy hooks are stubbed in Phase 2, filled in Phase 3. Phase 2 writes apply_privacy() as a pass-through. Phase 3 replaces the body only. No Phase 2 file is restructured later.
  4. Every module gets a smoke block. Each file ends with if __name__ == "__main__": running a tiny self-check on synthetic input. At test time you run modules bottom-up, so a failure localises to one file instead of one traceback from the top.

On the LOC figure

Earlier I estimated ~550 lines. That was the core algorithmic code only. The ~1,400 here includes config, the two dashboards, scripts, smoke blocks and docstrings. The algorithms themselves have not grown — this is not scope creep, it is the honest total once boilerplate is counted.

How this relates to the 12-week plan

The four lanes in the week-by-week plan are who does what. These four phases are what gets written when. They are different cuts of the same work: Phase 1 lands in weeks 1–4, Phase 2 in weeks 3–6, Phase 3 in weeks 7–8, Phase 4 in weeks 9–10. Your team still splits by lane; I write the code in phases.

The four phases

Strictly sequential · each depends on the one before

Phase 1

Foundation & data

8 files · ~340 LOC

Everything needed to turn images into the arrays the rest of the project consumes. This phase also fixes the contracts and writes the README, so the shape of the whole codebase is settled before any learning code exists.

Builds
  • config.py — dataclass with every hyperparameter, seed, path
  • contracts.py — shape assertions used everywhere
  • data/loader.py — LFW via scikit-learn, CelebA subset, unified index
  • data/degrade.py — downsample → motion blur → noise → JPEG, parameterised
  • data/partition.py — 5 nodes, disjoint identities, per-node degradation ranges
  • models/backbone.py — three interchangeable embedders behind one interface
  • scripts/01_prepare_data.py, requirements.txt, README.md
Key decisions inside
  • Backbone selected by config: insightface → facenet → dummy, tried in that order with automatic fallback
  • DummyBackbone generates identity-structured random vectors so downstream phases never block on an install
  • Degradation parameters are sampled per node, not per image — that is what creates the non-IID condition
  • All randomness seeded from config for reproducible figures
Hands forward Four .npy files, one partition.json, and a config object. From here, Phase 2 never touches an image.
Phase 2

Learning core

5 files · ~400 LOC

The adapter, the federated loop, and the metrics. This phase produces the project's headline result, so it is the largest and the one worth reading most carefully when you verify.

Builds
  • models/adapter.py — 512→256→512 residual MLP, ~0.4 M params
  • fl/node.py — local training on a node's slice, returns a weight delta
  • fl/server.py — FedAvg aggregation + the privacy hook
  • fl/loop.py — three modes: centralised, local_only, federated
  • eval/metrics.py — rank-1, TPIR at fixed FPIR, DET curve points
Key decisions inside
  • All three training modes share one code path, differing only in how data is partitioned and how updates are combined — so the three-way comparison is apples to apples by construction
  • Cosine-embedding loss on (degraded, clean) pairs of the same identity, hard negatives mined within the node's own slice
  • Optional FedProx term present but disabled by default in config
  • Round history logged to JSON so convergence curves come free
# fl/server.py — written in Phase 2, body filled in Phase 3 def apply_privacy(update, cfg): """Phase 3 replaces this body. Signature is frozen.""" return update
Hands forward A trained adapter, a working federated loop with a pass-through privacy hook, and reusable metrics. At this point the project's core claim is already implementable — everything after is contribution and demo.
Phase 3

Privacy & experiments

4 files · ~310 LOC

The three privacy mechanisms, plus the runner that turns everything into the tables and figures your report needs. No Phase 2 file is restructured — apply_privacy() gets a real body, and that is the only edit.

Builds
  • privacy/dp.py — clip update to a fixed L2 norm, add Gaussian noise, log the ε accounting
  • privacy/mask.py — pairwise seeds, one node adds, the partner subtracts, masks cancel in the sum
  • privacy/template.py — top-96 dimension select, mean-threshold binarise, XOR with a per-node key
  • eval/experiments.py + scripts/02_run_experiments.py
Experiments it runs
  • Clean vs degraded accuracy — the problem-statement chart
  • Local-only vs federated vs centralised — the headline chart
  • Noise sweep — the privacy–utility curve
  • Template k sweep — the accuracy cost of protection
  • Masked-update dump — the "server sees nothing" screenshot
  • Optional: FedAvg vs FedProx, membership inference
Hands forward Every number and figure the report needs, written to results/ and figures/, plus a saved adapter for Phase 4 to load.
Phase 4

Video pipeline & dashboards

6 files · ~430 LOC

The demo. Consumes the trained adapter and the template code from earlier phases and puts a face on the whole system — literally.

Builds
  • pipeline/detect.py — read video, detect faces, assign track IDs
  • pipeline/quality.py — reject on eye distance, blur variance, pose
  • pipeline/match.py — embed → adapt → compare to template → k-of-n track vote
  • apps/server_app.py — upload probe, mint template, push, view alerts
  • apps/node_app.py — review queue, confirm / reject, writes labels back
  • scripts/03_run_video.py — annotated output video
Key decisions inside
  • Node and server communicate through a shared SQLite file, not a network — one less thing to break during a live demo
  • Track vote thresholds live in config so you can tune them in front of the examiner if asked
  • Both apps run from one command each; no build step
  • Video writer produces the backup demo recording as a side effect
Hands forward A runnable end-to-end demo. Build complete — testing starts here.

T1 through T3 need no dataset and no face model, so most of the codebase is verifiable within minutes of Phase 4 landing. T4 is the one genuine environment risk, and it is deliberately isolated so that failing it invalidates nothing built before it.

What deferred testing costs, and the mitigation

RiskMitigation already in the plan
A Phase 1 shape mistake propagates through all four phasescontracts.py asserts shapes at every boundary, so the failure surfaces at the boundary that broke it rather than three modules downstream.
The face model will not install, and nothing can be testedDummyBackbone. T1–T3 pass without any model, dataset or image.
Phase 3 forces a rewrite of Phase 2The apply_privacy() signature is frozen in Phase 2 and only its body changes.
Phase 4 needs something Phase 2 did not saveThe contract table above fixes adapter_final.pt and the template format before Phase 2 is written.
One giant traceback with no idea which file brokePer-module smoke blocks, run bottom-up as T1.
A library API differs from what was assumedThe honest residual risk. Most likely in insightface and the tracker. Both are isolated to one file each — backbone.py and detect.py — and both have a documented fallback.

The one thing I would change if you let me

Running T1–T3 immediately after Phase 2 instead of after Phase 4 costs about ten minutes and catches the entire class of shape-and-plumbing errors while only two phases exist to search through. It does not break your "test at the end" preference for anything real — no dataset, no model, no results. If you would rather keep the build completely uninterrupted, that is fine and the plan works as written; the dummy backbone exists precisely so this is a preference and not a requirement.

What I need from you before starting

  1. Sign off the phase split, or tell me to move work between phases.
  2. Confirm the nine contracts in the table above — particularly the 96-bit template and the 512-d embedding width, since those two touch every phase.
  3. Confirm 5 nodes as the default. Changing it later is a config edit, but the figures are laid out for five.
  4. Tell me the backbone preference: attempt insightface first, or go straight to facenet-pytorch for a quieter install on Windows.
  5. Say whether the T1–T3 checkpoint after Phase 2 is acceptable, or whether you want all four phases uninterrupted.

Once you confirm, I start with Phase 1 and stop at its boundary rather than continuing on.
