The dataset split

Exactly as instructed · now enforced in code

70%CENTRAL SERVER
20%TRAIN
10%VAL
70% central serverGallery and held-out evaluation. Reference photographs that arrive with a case report, plus the identities used to measure the system. Nobody trains on it.
20% node trainingSplit across 5 nodes. Each node trains only on its own share, and it never leaves the node.
10% node validationLocal validation at each node, from the same identities that node trains on.

It lives in fedmps/config.py as three numbers that must sum to 100, and the code refuses to start if they do not:

server_pct = 70.0 # gallery + evaluation, never trained on node_train_pct = 20.0 # local training, stays at the node node_val_pct = 10.0 # local validation, stays at the node

Run this in front of him if he wants to see it is not just a slide:

python -c "from fedmps.config import default_config; print(default_config().partition.summary())"

One thing to say before he asks

The server's 70% is not training data. In federated learning the server holds none — that is the whole premise. Its share is the gallery and the evaluation set: the reference photographs, and the held-out people used to measure whether the system works. If you let the server train on 70% of the faces, you have rebuilt the centralised system the project exists to avoid. Say this yourself, early, rather than letting it surface as a challenge.

And the detail that earns marks

The split is by identity, not by image. Every photograph of one person lands on one side of the line. Split by image instead and the same face appears in both training and evaluation, which inflates every number in the report. This is the single most common flaw in student face-recognition work, and being able to say you avoided it deliberately is worth more than a percentage point of accuracy.

Why 67.2% and not exactly 70%

Because the split is by identity and people have different numbers of photographs. Asking for 70% of identities gives 67.2% of images — the two cannot both be exact at once, and identity is the one that has to be, or the evaluation leaks.

Volunteer this if the arithmetic comes up. It shows you know which of the two constraints matters and why you chose it, rather than having missed a rounding error.

The demo

Six steps · the order matters, step 3 is the point of the whole thing

Show the split

python -c "from fedmps.config import default_config; print(default_config().partition.summary())"

Then open figures/fig1_degradation.png.

"The dataset is split 70/20/10 as you asked. The server's 70% is gallery and evaluation — it never trains on anything. The 30% goes across five nodes, two thirds for training and one third for validation. And we split by person, not by photograph, so nobody the system is tested on was ever seen during training."
The three percentages printed straight from the config, then the chart showing what surveillance degradation costs a state-of-the-art face model.
~60 seconds

Open a missing-person case

On the server console → Open a case tab. Enter a name, upload media/person.jpg, set nodes to 5, press Create case and distribute.

"This is a report coming in. I upload the photograph once. Watch what actually leaves this machine."
A table of five rows — one per node — each holding a different 64-byte hexadecimal string for the same person. No image is stored or sent.
"Sixty-four bytes per site, and every row is a different pattern for the same face. Two sites cannot compare their watchlists and work out they are looking for the same person."
~90 seconds

Run a node against its camera

python fedmps/scripts/03_run_video.py \ --video media/corridor.mp4 --node 0

Then, while it runs, switch to the server console → Confirmed sightings.

"The node is now watching its own footage. Detection, tracking, a quality gate, then matching against those 64 bytes. It has found someone — and here is the part that matters."
The terminal reports an ALERT … PENDING local review. The server's Confirmed sightings tab is empty.
"The node is holding a face crop right now. The server cannot see it. Nothing reaches this screen until a named person at that site looks at it and agrees."
~2 minutes · the centrepiece

Show what the node can and cannot see

On the node console → Watchlist tab. Then back to Review queue.

"This is everything the node knows about who it is looking for. A keyed code and a key fingerprint. It is searching for a person whose face it has never been shown."
A single row: case reference, 64-byte hex template, key fingerprint. No photograph anywhere on the page.
~60 seconds

The human gate

On the node console, set Reviewing as to a real name, then press Confirm — send upstream. Switch to the server console and reload.

"The operator reviews the crop and confirms it. Only now does it travel — and the server records who authorised it."
The sighting appears under Confirmed sightings with the crop, the score, the camera, and confirmed by the operator's name.
"Every disclosure has a human attached to it, and it is in an audit log that the site operators can read too. Trust runs both directions or it does not mean anything."
~90 seconds

Close the case

On the server console → Cases → Close & revoke. Then reload the node console → Watchlist.

"The person is found, so I close the case. Every template issued for it is revoked at the same moment."
The node's watchlist is now empty.
"Nobody had to remember to delete anything. Cases also carry an expiry date, so a watchlist cannot quietly outlive the reason it was created."
~60 seconds

If you only have three minutes

Run steps 2, 3 and 5. Distribute a case, show the alert sitting unseen by the server, then confirm it and watch it arrive. That sequence alone demonstrates the privacy architecture end to end.

Questions he is likely to ask

Answers in your own words · the honest ones land best

Why does the server get 70% if it does not train on anything?

Because evaluation needs to be generous and training does not. The server's share is the held-out population — hundreds of people the system has never seen — which is what makes the accuracy figure trustworthy. A small evaluation set gives a number that swings on a handful of images.

The nodes' 30% is deliberately the scarce side. That is the realistic case: a single hospital or campus has a modest amount of camera data, and the whole argument for federation is that it lets many such sites learn together without pooling.

Is this real federated learning, or just simulated?

The learning is real: five nodes with disjoint identities and different camera characteristics, training locally and sharing only weight updates. The averaging, the proximal term, the clipping, the noise and the masking all run exactly as they would in deployment.

What is simulated is the network. The five nodes are processes on one machine rather than five buildings. Say so plainly — it is a standard research setup, and pretending otherwise invites a question you cannot answer.

Why freeze the face-recognition model instead of training it?

Because it cannot be trained at this scale. ArcFace is trained on millions of images with a classifier spanning every identity it knows; a node with a few hundred images has neither. Federating it would also mean shipping 166 MB per site per round.

So we freeze it and federate a small adapter that corrects for each site's camera. That is the project's actual contribution, and it is why the update is 265 KB instead of 166 MB.

Did you split by image or by person?

By person. Every photograph of one individual sits on one side of the split. If you split by image, the same face appears in training and testing and the accuracy figure becomes meaningless.

You can show it: the partition code asserts that no identity and no image index is shared between any node and the evaluation set, and it fails loudly if that is ever violated.

What stops the server from seeing the faces?

Three separate things, and they defend different attacks. Raw video and embeddings never leave the node at all. Model updates are masked so the server sees only the sum across nodes, never one site's update. And the watchlist itself travels as a keyed code rather than a photograph.

Be precise about the limit: a confirmed alert does send one face crop upstream. That is deliberate and necessary — an alert nobody can look at is useless — and it happens only after a named operator approves it.

What if a node is compromised?

The keyed template protects the watchlist database at rest and stops two sites correlating their lists. It does not protect against a live compromised node, which holds the key and is watching its own camera anyway.

Saying this unprompted is worth more than claiming otherwise. The mitigation is revocation: close the case, reissue under a new key, and every template that node holds becomes useless.

Why is the accuracy not higher? The papers report 97%.

Those are balanced-set accuracies, where every test face is in the gallery. The real task is open-set: almost everyone walking past a camera is on no watchlist, and the system has to stay quiet for all of them.

We report true positives at a fixed false-alarm rate instead, which is far less flattering and far more useful. One camera seeing 2,000 people a day against a 50-person watchlist makes 100,000 comparisons; at a false-positive rate any paper would call excellent, that is a hundred false alarms a day. That is why the system decides per track rather than per frame, and why a human confirms every alert.

Is the demo video real footage?

No — it is built from held-out faces so the test is reproducible and the person in it is someone no node trained on. Say so.

If you have recorded your own corridor footage by then, show that instead: four consenting team members, filmed by yourselves, no bystanders. That is the honest version and it needs no ethics approval because you are the subjects.
